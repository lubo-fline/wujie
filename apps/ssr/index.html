NESTJS · SSR LAB

SSR 解剖台

掘金那篇《用 NestJS 构建的 SSR 混合渲染方案》的落地版：一个 Node 进程同时当 BFF 和渲染器。 Controller 只返数据，拦截器把 React 组件 renderToString 塞进模板字符串，浏览器再 hydrateRoot 接管。 下面的 HTML、状态、耗时全部来自真实运行的服务端，不是手写的示意。

拦截器用 map 把四件事串成管道：样式 → hydrate 脚本 → SEO → 渲染。点一下走一遍，每段的真实产出会依次点亮。

05 这套方案的账单

    
实测数字来自这台机器上真实跑的服务；下面四条是它的隐性成本，选型前最好先认下来。

    

    
    
      
  • ✖renderToString 是同步的，会占住事件循环。首页 10ms 不算事，页面一大就到几十毫秒，并发上来直接排队。上量要么缓存渲染结果，要么换 renderToPipeableStream 流式输出。
    • 
      
  • ✖CSS 得手写 link 列表。没有构建器帮你收集依赖图，哪页要哪些样式自己报（上面 Controller 里的 links 字段）。等于把自动化的活接回手上，这是省掉 Vite 的隐性成本。
    • 
      
  • ✖状态注入必须转义。数据里出现 </script> 就会提前关标签，后面的 hydrate 脚本一起废（点上面「不转义」看现场）。
    • 
      
  • ✓但收益也实在：首屏就是完整 HTML，SEO 与社交分享直接可用；BFF 和页面同进程，取数少一跳；两个文件的体积就能起一个站点，没有 Vite/Next 那套基建。
